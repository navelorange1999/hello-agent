# Project: 本地知识库（Mini RAG）

## 为什么做这个项目？

这是 Phase 1 的毕业项目，它把你之前学的所有东西串联起来：Python async 处理并发文档加载，Pydantic 管理配置，API 调用与 LLM 通信，Embedding 做检索。你将构建一个完整的 RAG 系统——这是 Agent 最重要的能力之一。

---

## 项目目标

构建一个本地知识库问答系统：

1. 加载本地文档（Markdown / TXT / PDF）
2. 智能切分文档为合适的 Chunk
3. 将 Chunk 向量化并存入本地向量数据库
4. 实现语义检索 + LLM 生成的问答流程
5. 评估检索质量和回答准确性

---

## 任务拆解

### Task 1：文档加载与切分（Day 1-2）

- [ ] 实现文档加载器：支持 .md、.txt 至少两种格式
- [ ] 实现多种切分策略并对比：
  - 按固定字符数切分（CharacterSplitter）
  - 按段落/标题切分（递归切分）
  - 按语义切分（句子聚合直到语义发生跳变）
- [ ] 实现 chunk overlap（重叠窗口）
- [ ] 准备一组测试文档（推荐：用你自己的学习笔记）
- [ ] **对比实验**：同一文档用不同策略切分，然后检索同一个 query，看结果差异
- [ ] **思考**：chunk 太大或太小分别有什么问题？

### Task 2：向量存储（Day 2-3）

- [ ] 安装 ChromaDB 并理解其基本概念（Collection、Document、Embedding）
- [ ] 将切分好的 chunk 向量化并存入 ChromaDB
- [ ] 实现 metadata 存储：每个 chunk 记录来源文件、页码/行号、切分方式
- [ ] 实现增量更新：文档修改后只重新处理变更的部分
- [ ] **对比**：尝试用 FAISS 实现同样的功能，体验它和 ChromaDB 的 API 设计差异

### Task 3：检索与问答（Day 3-4）

- [ ] 实现基础检索：给定 query，返回最相关的 Top-K 个 chunk
- [ ] 将检索到的 chunk 作为 context 注入 prompt，调用 LLM 生成回答
- [ ] 实现 "引用溯源"：回答中标注信息来源于哪个文档的哪个部分
- [ ] 处理"知识库中没有答案"的情况——LLM 应该说"我不知道"而不是编造
- [ ] **笔记**：画出完整的 RAG 流程图：Query → Embed → Search → Context → LLM → Answer

### Task 4：评估与优化（Day 4-5）

- [ ] 准备一个评估集：10-20 个问题 + 标准答案 + 相关文档标注
- [ ] 评估检索质量：相关文档是否被检索到？（Recall@K）
- [ ] 评估回答质量：回答是否正确且基于检索到的内容？
- [ ] 尝试优化：
  - Query 改写（将用户问题改写为更适合检索的形式）
  - 混合检索（向量检索 + 关键词检索）
  - Reranking（用另一个模型对检索结果重排序）
- [ ] **总结**：哪些环节对最终效果影响最大？你的改进哪些有效哪些无效？

## 验收标准

- [ ] 能加载至少 10 个文档，切分并存入向量数据库
- [ ] 能对自己的知识库进行问答，回答基于真实文档内容
- [ ] 有量化的评估结果：检索 Recall 和回答准确率
- [ ] 能画出完整的 RAG 架构图，并解释每个环节的作用和优化空间
- [ ] 能向别人解释：为什么 RAG 是当前 Agent 获取知识的主流方案？

## 延伸思考

> 你现在构建的是一个单轮问答 RAG。但在 Agent 场景中，往往需要多轮对话的 RAG——Agent 的第一次检索可能不够准确，它需要根据初次结果追问或换个关键词重新检索。这种"自主决定是否需要更多信息"的能力，就是 Agent 和普通 RAG 的关键区别。
