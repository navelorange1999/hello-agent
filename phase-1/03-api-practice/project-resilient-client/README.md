# Project: 弹性 API 客户端

## 为什么做这个项目？

生产环境中，LLM API 会遇到各种问题：Rate Limit（429）、服务过载（529）、网络波动、超时。如果你的 Agent 遇到一个错误就崩溃，那就不是一个可靠的产品。这个项目让你构建一个"打不死"的 API 客户端。

---

## 项目目标

构建一个生产级的 LLM API 客户端：

1. 指数退避重试策略（Exponential Backoff）
2. 熔断器模式（Circuit Breaker）
3. 多模型 Fallback（主模型不可用时自动切换）
4. 请求级的超时控制和取消
5. 使用指标和成本追踪

---

## 任务拆解

### Task 1：重试策略（Day 1）

- [ ] 实现指数退避重试：第一次等 1s，第二次 2s，第三次 4s...
- [ ] 加入抖动（Jitter）避免"惊群效应"
- [ ] 区分可重试错误（429, 529, 网络超时）和不可重试错误（401, 400）
- [ ] 设置最大重试次数和最大等待时间
- [ ] **思考**：为什么要加 Jitter？如果 100 个 Agent 同时触发重试，不加 Jitter 会怎样？

### Task 2：熔断器模式（Day 2）

- [ ] 理解熔断器的三个状态：Closed（正常）→ Open（熔断）→ Half-Open（试探）
- [ ] 实现一个 CircuitBreaker 类：连续失败 N 次后进入 Open 状态
- [ ] Open 状态下直接返回错误，不发送请求（保护 API）
- [ ] 设定冷却时间后进入 Half-Open，允许一个试探请求
- [ ] **笔记**：画出熔断器的状态机图

### Task 3：多模型 Fallback（Day 2-3）

- [ ] 定义模型优先级列表（如 Claude Sonnet → GPT-4o → Claude Haiku）
- [ ] 主模型失败或超时后自动切换到备用模型
- [ ] 实现统一的消息格式转换层（不同 API 的消息格式不同）
- [ ] 记录每次 fallback 的日志，用于后续分析
- [ ] **思考**：Fallback 到不同模型时，Agent 的行为可能会不一致。你会怎么处理？

### Task 4：可观测性与成本追踪（Day 3-4）

- [ ] 为每次 API 调用记录：延迟、token 数、模型、是否重试、费用
- [ ] 实现一个简单的 metrics 聚合：平均延迟、成功率、总成本
- [ ] 添加请求 ID（request_id）用于调用链追踪
- [ ] 实现并发限流器（Token Bucket 或 Sliding Window）
- [ ] **延伸**：将 metrics 输出为 JSON，可以后续接入 Grafana 等监控系统

---

## 验收标准

- [ ] API 返回 429 时能自动重试且不 crash
- [ ] 连续失败 5 次后熔断器打开，停止发送无意义的请求
- [ ] 主模型不可用时自动切换备用模型，用户无感知
- [ ] 能出具一份包含成功率、平均延迟、成本的统计报告
- [ ] 能向别人解释：生产级 Agent 的 API 调用需要考虑哪些可靠性问题？

## 延伸思考

> 你现在构建的这个弹性客户端，在 Agent 框架中通常叫 "LLM Provider" 或 "Model Client"。去看看 LangChain 的 `ChatAnthropic` 类，看看它在可靠性方面做了什么（和没做什么）。
