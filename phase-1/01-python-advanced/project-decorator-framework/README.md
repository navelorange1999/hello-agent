# Project: 装饰器工具注册框架

## 为什么做这个项目？

打开 LangChain 的源码，你会看到 `@tool` 装饰器；打开 MCP Server 的代码，你会看到类似的 `@server.tool()` 注册模式。**装饰器是 Agent 框架中最核心的设计模式之一**——它让开发者用一行注解就能把普通函数变成 Agent 可调用的工具。

理解装饰器，就是理解 Agent 框架的骨架。

---

## 项目目标

构建一个迷你"工具注册框架"：

1. 用装饰器将普通函数注册为"工具"
2. 自动提取函数签名、docstring 作为工具描述
3. 支持参数校验和返回值包装
4. 实现一个简单的"工具路由器"——根据名称调用对应工具

---

## 任务拆解

### Task 1：装饰器基础（Day 1）

- [ ] 实现一个最简单的计时装饰器，测量函数执行时间
- [ ] 实现带参数的装饰器（如 `@retry(max_attempts=3)`）
- [ ] 使用 `functools.wraps` 保留原函数的元信息
- [ ] **笔记**：画出装饰器的执行流程——`@decorator` 语法糖背后发生了什么？

### Task 2：工具注册器（Day 1-2）

- [ ] 创建一个 `ToolRegistry` 类，内部维护一个工具字典
- [ ] 实现 `@registry.tool` 装饰器，将函数注册进字典
- [ ] 自动从函数的 `__name__`、`__doc__`、type hints 中提取工具元信息
- [ ] 实现 `registry.list_tools()` 列出所有已注册工具及其描述
- [ ] **思考**：打开 LangChain 的 `@tool` 装饰器源码，和你的实现对比一下

### Task 3：参数校验层（Day 2）

- [ ] 利用 `inspect.signature` 获取函数参数信息
- [ ] 在调用工具前自动校验参数类型是否匹配
- [ ] 校验失败时返回清晰的错误信息（而不是 crash）
- [ ] **思考**：Agent 在调用工具时，LLM 生成的参数经常类型不对（比如该传 int 传了 str），你的校验层能怎么处理？

### Task 4：工具路由器（Day 3）

- [ ] 实现 `registry.call(tool_name, **kwargs)` 方法
- [ ] 支持同步和异步工具（检测函数是否是协程）
- [ ] 添加调用日志：记录每次工具调用的输入、输出、耗时
- [ ] 写一个演示脚本：注册 5 个工具，模拟"Agent 选择并调用工具"的流程
- [ ] **延伸**：如果要支持工具的 JSON Schema 描述（类似 OpenAI Function Calling 的格式），你会怎么扩展？

---

## 验收标准

- [ ] 用 `@registry.tool` 一行代码即可注册新工具
- [ ] `registry.list_tools()` 输出的格式清晰、包含参数和描述
- [ ] 参数类型错误时不会 crash，而是返回有意义的错误
- [ ] 能向别人解释：为什么 Agent 框架都喜欢用装饰器模式？

## 延伸思考

> 你现在构建的这个迷你框架，其实就是 LangChain `@tool`、MCP `@server.tool()`、OpenAI Function Calling 的简化版本。完成后，去读读这些框架的真实实现，你会发现它们在你的基础上多做了什么。
